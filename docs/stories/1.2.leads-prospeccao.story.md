## Story

**Como** vendedor usando o CRM Produto Digital,
**eu quero** registrar leads no funil de prospecção do livro "Prospecção Fanática" (estágio, qualificação, familiaridade) e toda tentativa de contato feita com eles,
**para que** eu consiga aplicar a metodologia do livro (Pirâmide da Prospecção, Quatro Objetivos, taxonomia RDO) dentro do sistema em vez de controlar isso em planilha, e ter as métricas diárias de atividade (Eficiência + Eficácia) por escrito.

## Acceptance Criteria

1. Existe um model SQLAlchemy `Lead` em `app/models/lead.py` com todos os campos e enums definidos em `docs/architecture/prospeccao-fanatica-schema.md#lead`, incluindo `customer_id` como FK nullable para `customers.id`.
2. Existe um model SQLAlchemy `AtividadeProspeccao` em `app/models/atividade.py` com todos os campos e enums definidos em `docs/architecture/prospeccao-fanatica-schema.md#atividadeprospeccao`, com `lead_id` como FK obrigatória para `leads.id`.
3. Existe um model SQLAlchemy `MetricaDiaria` em `app/models/metrica_diaria.py` conforme `docs/architecture/prospeccao-fanatica-schema.md#metricadiaria`, com `data` como coluna `date` única (constraint `unique=True`).
4. `app/models/__init__.py` é atualizado para importar `Lead`, `AtividadeProspeccao` e `MetricaDiaria` (nos moldes do que já está comentado para `Customer`/`Order`/etc.), e o comentário referente a `Interaction` é removido (substituído por `AtividadeProspeccao`, conforme decisão em `docs/architecture/prospeccao-fanatica-schema.md`).
5. Alembic é inicializado no projeto (`alembic init` ou equivalente manual), configurado para ler `DATABASE_URL` de `app.config.settings` e usar `app.database.Base.metadata` como alvo de autogenerate.
6. Uma migration Alembic é gerada e aplicada com sucesso contra o Supabase do projeto (`aws-0-sa-east-1.pooler.supabase.com`, projeto `crm-produto-digital-aiox`), criando as 3 tabelas novas (`leads`, `atividades_prospeccao`, `metricas_diarias`) sem alterar nenhuma tabela pré-existente do Supabase.
7. Rodar `uvicorn app.main:app` continua subindo sem erro após a mudança (o `init_db()` em `app/database.py` não deve tentar recriar tabelas já cobertas por migration — ver Dev Notes sobre isso).
8. Os models `Customer`, `Order`, `Student`, `RecoveryLead` mencionados no README **não** são criados nesta story — ficam para uma story futura do módulo pós-venda. Esta story cobre exclusivamente a camada de prospecção.

### Refactoring Performed

- **Arquivo**: `app/models/atividade.py`
  - **Mudança**: adicionado `index=True` na coluna `lead_id`
  - **Por quê**: FK sem índice em Postgres não ganha índice automático (só PK ganha). Essa tabela vai ser consultada constantemente por `lead_id` ("todas as atividades deste lead") — sem índice, isso seria um table scan já nas primeiras centenas de linhas.
  - **Como**: index criado, migration regenerada do zero (era mais limpo que uma segunda migration corretiva pra algo nunca aplicado fora desta sessão de teste), reaplicado o fix de `DROP TYPE` no novo arquivo de migration (autogenerate não preserva edições manuais entre regenerações), e revalidei o ciclo upgrade/downgrade/upgrade — passou limpo com o índice presente (`ix_atividades_prospeccao_lead_id` confirmado via `\d`).
