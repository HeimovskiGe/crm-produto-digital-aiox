## Story

**Como** vendedor usando o CRM,
**eu quero** que o kanban mostre o funil operacional das aulas do Lucas Carmo (Prospecção → Follow → Qualifica/Desqualifica → Assentamento → Reunião de Venda → Negociação → Fechado) em vez do funil de qualificação do livro, com a Pirâmide do livro virando uma etiqueta no card,
**para que** o CRM reflita como eu realmente conduzo uma venda (processo), não só o quão quente o lead está (qualificação) — as duas coisas coexistem, mas o processo é o que preciso ver todo dia.

## Dev Notes

**Por que duas dimensões de estágio no Lead**: `etapa_processo` (novo, funil operacional das aulas) e `pipeline_stage` (existente, Pirâmide do livro) medem coisas diferentes e coexistem — um lead pode estar `assentamento` (processo) e `janela_identificada` (qualificação) ao mesmo tempo. Decisão do usuário em 2026-09-16: `etapa_processo` vira a coluna do kanban, `pipeline_stage` vira badge. Ver `docs/architecture/prospeccao-fanatica-schema.md` para a justificativa completa.

**`ALTER TYPE ... ADD VALUE` e transação**: Postgres (desde a v12) permite `ALTER TYPE ... ADD VALUE` dentro de uma transação, DESDE QUE o valor novo não seja lido/comparado na mesma transação. Como esta migration só adiciona o valor e não faz nenhum `SELECT ... WHERE objetivo_contato = 'assentamento'` no mesmo `upgrade()`, é seguro. Não tentar fazer isso fora de uma migration do Alembic (ex: direto num script Python) sem entender essa regra.

**Paleta `.tag` já existe como referência**: `pam-geh/prudentopolis-kanban/index.html` tem exatamente esse padrão (`<span class="tag">`, com variantes `.tag.nova`, `.tag.wa`, `.tag.ia` coloridas por tipo) — reaproveitar esse padrão visual pro badge de qualificação em vez de inventar um novo.

**`app/models/__init__.py` e `alembic/env.py`**: mesma pegadinha da story 1.2 — os models novos (`ReuniaoVenda`, `Referido`) só entram no `Base.metadata` se forem importados em `__init__.py` ANTES do autogenerate rodar. Já está resolvido desde a story 1.2 (o `env.py` importa `app.models`), só não esquecer de atualizar o `__init__.py` primeiro (Task 1 antes da Task 2).

**Endpoint renomeado (`meta/stages` → `meta/qualificacao`)**: como é a mesma sessão/dev que também é o único "cliente" desse endpoint (o `app.js` deste mesmo repo), renomear é seguro — não existe integração externa consumindo isso ainda.

**Fora de escopo (vira story futura)**: tela de "modo reunião" pra rodar os 7 passos ao vivo (com timer, toggle de DI, captura de referido) precisa de bem mais UI do que cabe aqui — só a fundação de dados (`ReuniaoVenda`, `Referido`) é desta story.

### Completion Notes List

- **Bug real encontrado e corrigido**: `op.add_column()` numa tabela já existente (`leads`) com uma coluna `Enum` **não cria o tipo ENUM sozinho** — diferente de `create_table`, que cria o tipo automaticamente. O autogenerate gerou `op.add_column('leads', sa.Column('etapa_processo', sa.Enum(...)))` sem criar `etapa_processo_enum` antes, e o upgrade falhava com `type "etapa_processo_enum" does not exist`. Corrigido criando o tipo explicitamente via `postgresql.ENUM(...).create(op.get_bind(), checkfirst=True)` antes do `add_column`.
- **Erro de processo meu, não do código**: ao testar o ciclo upgrade/downgrade/upgrade a primeira vez, rodei os 3 comandos em sequência sem checar o código de saída do primeiro (que falhou). O `downgrade -1` seguinte acabou revertendo a migration ANTERIOR (1.3), não a nova, porque o `alembic_version` nunca avançou. Isso apagou as tabelas das stories 1.2/1.3 temporariamente (sem perda real, era ambiente de teste vazio). Refeito com `set -e` entre os passos — ciclo completo confirmado limpo depois do fix.
- `etapa_processo` adicionado com `server_default='prospeccao'` na migration (não só default do Python) — necessário porque é `NOT NULL` numa tabela que já existe; o default é removido logo depois (`alter_column ... server_default=None`) pra manter o padrão do projeto de defaults só no lado do ORM.
- `ALTER TYPE objetivo_contato_enum ADD VALUE IF NOT EXISTS 'assentamento'` aplicado sem recriar o tipo — testado, e o `downgrade()` documenta explicitamente que esse valor específico NÃO é removido no downgrade (Postgres não tem `DROP VALUE` nativo).
- **Não consegui testar visualmente no navegador nesta story** — a extensão Claude in Chrome não conectou. Validei via `curl` (todos os endpoints, incluindo o badge de qualificação embutido no `LeadOut`) e revisão de código; a lógica de `renderKanban()` segue o mesmo padrão já testado visualmente na story 1.3, só trocando o campo de agrupamento e adicionando o badge. Recomendo ao @qa (ou ao usuário) confirmar visualmente antes de fechar como Done, se possível.
- `ReuniaoVenda`/`Referido`: só schema, sem endpoints — conforme AC10, fica pra story futura.
